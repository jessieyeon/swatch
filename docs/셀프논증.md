### 쟁점 1 — AI 컬러 추출 기능을 어디까지 보여 줄까

| 칸 | 내용 |
| --- | --- |
| 내 주장 | 사진을 넣으면 컬러를 자동으로 추출해 색상 값을 저장해준다. |
| 반론(AI) | 실제 추출은 ‘실제 비즈니스 로직’, 색상 값 저장은 ‘영구 저장’이라 각각 −5 감점 대상이다. 또 사용자가 자동 추출된 5색을 그대로 믿을지, 원하는 색을 직접 고르고 싶어 할지는 리뷰로 확인되지 않았다. |
| 반론(내가 찾은 것) | Pinterest 리뷰 500건 중 색·컬러 언급 0건. 범위를 디자인 생성 앱(Canva)까지 넓혔지만 App Store 한국·미국 각 500건, Play 한국 약 6,000건에서도 ‘색을 참고하는 기능’을 평가한 리뷰는 없었다(가장 가까운 것도 “폰트와 색상, 스티커도 엄청 종류 많아서” 2022-07-25 ★5 — 종류가 많다는 칭찬). |
| 재반론·수정 | Canva의 ‘이미지에서 팔레트 생성’ 기능을 근거로(P04 업계 관행) 유지하는 안도 검토했지만, 사용자 리뷰로 확인되지 않은 기능을 핵심 과업에 두는 것은 끼워맞추기라고 판단했다. 구현하면 실제 로직·영구 저장 감점 위험도 있다. |
| 결론 | **폐기** — 컬러 추출·컬러 칩 관련 화면과 과업을 모두 뺀다. |
| 근거(P번호·리뷰) | 리뷰 근거 없음(Pinterest 0/500, Canva 약 7,000건 중 해당 없음) · 안내문 4장 감점(실제 비즈니스 로직 · 영구 저장) · P08 미니멀 디자인 — 근거 없는 기능을 더하지 않는다 |
| 전·후 화면 | 해당 없음(기획 단계에서 폐기) — 04장 ‘새로운 기능’에서 컬러 칩 줄 삭제 |

### 쟁점 2 — 대상 사용자를 ‘개발자’로 한정해도 되나

| 칸 | 내용 |
| --- | --- |
| 내 주장 | 대상 사용자는 다양한 레퍼런스를 수집하는 개발자다. |
| 반론(AI) | 레퍼런스를 가장 많이 모으는 건 디자이너다. 수집한 1단계 리뷰에는 개발자라고 밝힌 사용자가 없고, 오히려 일러스트 · 인테리어 · 네일처럼 비개발 용도가 많다. 개발자로 한정하면 리뷰 근거와 대상이 어긋날 수 있다. |
| 반론(내가 찾은 것) | 이제 직업의 경계선이 없어지고 있기 때문에 개발자도 많이 수집을 하고 있다. 그럼 개발자로 한정하지 말고 디자인 관련 종사자로 바꾸는건 어떨까 |
| 재반론·수정 | 디자이너 없이 UI를 직접 짜야 하는 상황일 때 레퍼런스를 수집해서 레이아웃과 색을 참고할 수 있다면 훨씬 더 좋은 결과물을 얻을 수 있다. 디자이너는 직접 만들 수 있기 때문에 디자이너 도구처럼 생성하는 기능이 필수적이지만 개발자는 그렇지 않다. 스와치는 참고용으로만 쓰는 앱이므로 대상을 개발자로 한정해도 괜찮다. (디자인 관련 종사자로 넓히면 디자이너 도구와 구분이 흐려진다는 AI 반론도 반영) |
| 결론 | **유지** — 대상은 개발자. ‘디자이너 없이 UI를 짜며 레퍼런스를 참고용으로만 쓰는 사람’이라는 근거를 보강한다 |
| 근거(P번호·리뷰) | P06 기억보다 인식 — 디자인 용어에 익숙하지 않은 개발자에게 ‘왜 좋은지’를 적어 두는 것이 다시 쓰는 단서가 된다 · 스와치에는 생성 기능이 없고 저장 · 이유 기록 · 다시 찾기만 있다 · 한계: 리뷰에서 직업을 개발자라고 밝힌 사용자는 없다(AI 반론을 그대로 남김) |
| 전·후 화면 | 해당 없음(기획 단계 쟁점) |

### 쟁점 3 — 왜 Pinterest인가&#32;

| 칸 | 내용 |
| --- | --- |
| 내 주장 | 레퍼런스를 저장하고 감상평까지 남길 수 있는 앱들은 리뷰가 거의 없었기 때문에, 저장 기능이 있고 많은 사용자를 확보한 Pinterest로 정했다. |
| 반론(AI) | Pinterest는 발견(피드) 중심 앱이지 수집 도구가 아니다 — 리뷰 대부분이 광고 · 추천 · 계정 이야기라 스와치의 문제와 안 맞을 수 있다. 또 감상평 · 색 추출에 대한 직접 리뷰가 없을 수 있다. |
| 반론(내가 찾은 것) | 하지만 레퍼런스 수집의 가장 중요한 단계는 발견이며 많은 사람들이 핀터레스트의 보드를 활용해 수집하고 있다. 또한 직접 리뷰가 없다는 점은 반론의 논점이 될 수 없다. 내가 생각하고 예상한 부분과 실제 사용자들이 겪는 문제점이 다를 수 있기 때문이다. |
| 재반론·수정 | 리뷰 범위를 ‘모으고 · 정리하고 · 다시 꺼내 쓰는’ 과정으로 한정하고, 직접 근거가 없는 기능은 간접 리뷰 + 닐슨 원칙으로 보강한다. (AI 초안 채택) |
| 결론 | **유지** — 비교 앱은 Pinterest, 리뷰 범위만 수집 · 정리 · 재사용으로 한정 |
| 근거(P번호·리뷰) | 1단계 리뷰 분류표(App Store 500건 중 범위 안 29건) · Google Play 500건 교차 확인(범위 안 34건, 같은 주제) · 최저점 ⑥ “보드에 핀이 너무 쌓이다보니까 찾고 싶은 핀이 어디 있는지 잘 모르겠어요” (2026-08-14 ★5) |
| 전·후 화면 | 해당 없음(기획 단계 쟁점) |

### 쟁점 4 — 저니의 AI 활용 기회: 저장할 때 유형을 자동으로 뽑아 줄까

| 칸 | 내용 |
| --- | --- |
| 내 주장 | AI 활용 기회는 저니에서 찾아야 하므로, 이미지 컬러 추출(저니와 무관) 대신 저장할 때 유형(포스터 · PPT · 타이포그래피 등)을 자동으로 뽑아 주면 왜 저장했는지 기억하는 데 도움이 된다. |
| 반론(AI) | ① 유형은 ‘무엇’이지 ‘왜 좋은지’가 아니다 — 근본 원인(이유를 기록할 구조가 없음)과 리뷰 #1(어떤 점이 좋았는지 메모)을 직접 해결하지 못한다. ② 컬러 추출을 ‘리뷰 근거 없음’으로 폐기한 기준과 같은지 설명이 필요하다(직접 요구 리뷰 0건, 간접 근거는 ⑥ ‘핀이 쌓여 찾기 어렵다’ · 정리 기능 부족). ③ AI가 틀리면 사용자가 고쳐야 해 일이 늘 수 있다(P03 · AI 출력 검증). ④ 실제 분류는 감점 — 넣는다면 미리 정한 가짜 응답, 또는 저니에만 기회로 적는다. |
| 반론(내가 찾은 것) |  |
| 재반론·수정 | ‘왜 좋은지’는 결국 이미지의 특징에서 출발한다. PPT라면 가독성이 중요해서 ‘폰트 계층이 잘 나뉘어 있어 좋다’, 포스터라면 ‘색감이 마음에 든다’처럼 유형을 알면 이유를 더 쉽게 떠올릴 수 있다. 다만 목적은 AI 반론대로 ‘분류 수고를 덜어 다시 찾기를 돕는 기능’으로 바꾼다. AI는 제안만 하고 확정은 사용자가 한다. 실제 구현은 하지 않고 저장 시트에 ‘추천: x, y’ + 입력칸으로만 보여 준다. |
| 결론 | **수정** — 유형 자동 추천을 ‘다시 찾기를 돕는 제안’으로 다시 정의하고, 제안 후 사용자 확정 방식으로 저장 시트(S3-2)에 넣는다. |
| 근거(P번호·리뷰) | ⑥ “보드에 핀이 너무 쌓이다보니까 찾고 싶은 핀이 어디 있는지 잘 모르겠어요” (2026-08-14 ★5) · 정리 기능 부족 리뷰 · P06 기억보다 인식 · P03 사용자 통제(제안만) · 안내문 감점(실제 로직) 회피 |
| 전·후 화면 | 전: 저장 시트에 유형 칸 없음(v1-plan) / 후: ‘추천: 포스터 · 타이포그래피’ + 유형 입력칸 (S-3 저장 시트 캡처, S3-2) |

### 쟁점 5 — 보관함 카드에 이유·제목을 보여 줄까, 사진만 보여 줄까

| 칸 | 내용 |
| --- | --- |
| AI 원안 | 카드 = 이미지 → 제목 → 저장 이유 2줄 → 태그 (P06 — 이미지만 보고 이유를 떠올리지 않게) |
| 내 주장 | 보관함에서는 사진만 보였으면 좋겠다. 제목과 이유 문장을 카드에서 뺀다. |
| 반론(AI) | 카드에서 이유가 사라지면 Pinterest의 ‘왜 저장했는지 모른다’(리뷰 #1)가 보관함에서 다시 생길 수 있다. 다만 이유는 S-2 상세와 S-6 검색 결과에 남아 있고, 넓은 화면에서는 카드를 누르면 오른쪽에 바로 보인다. |
| 재반론·수정 | 보관함은 시각적으로 훑어보는 곳이라 글자가 많으면 이미지 비교가 방해된다. 이유는 카드를 고른 뒤 상세(S-2)에서 읽고, 검색(S-6)에서는 이유로 찾는다. |
| 결론 | **수정** — 보관함 카드는 사진만. 제목·이유·태그는 S-2 상세에서 본다 |
| 근거(P번호·리뷰) | P08 미학적이고 미니멀한 디자인 — 화면에 그 순간 필요하지 않은 정보를 넣으면, 필요한 정보(보관함에서는 이미지)와 경쟁해 눈에 덜 띈다. 이유는 P06에 따라 S-2 상세와 S-6 검색 결과에서 계속 보인다. |
| 전·후 화면 | 전: 카드에 제목·이유·태그(v1-plan) / 후: 사진만 (S-1 보관함 캡처) |

### 쟁점 6 — 저장 시트에서 보드·태그를 직접 만들 수 있게 할까

| 칸 | 내용 |
| --- | --- |
| 내 주장 | 저장할 때 태그를 직접 쓸 수 있는 것처럼 보드도 직접 만들 수 있었으면 좋겠다. |
| 반론(AI) | ① 처음 구현에서는 태그도 고르기만 되고 직접 쓰기는 없었다 — 보드만 넣으면 일관성(P04)이 깨지므로 둘 다 넣어야 한다. ② 저장 시트에 선택지가 늘면 ‘한 번에 저장’(P07, Pinterest 잘된 점)이 느려질 수 있다. ③ 실제로 만들면 영구 저장(POST)이라 감점 — 화면에만 보이고 서버에는 저장하지 않아야 한다. ④ 태그를 자유롭게 만들면 ‘타이포’·‘타이포그래피’처럼 비슷한 태그가 중복돼 오히려 ⑥ 다시 찾기가 어려워질 수 있다. |
| 반론(내가 찾은 것) |  |
| 재반론·수정 | 사람들이 이미 정해져 있는 틀 안에서만 고르면 원하는 대로 분류할 수 없다. 반론 ①은 수용 — 일관성에 맞게 태그와 보드 둘 다 직접 만들 수 있게 한다. 반론 ②(속도)에는 — 저장할 때 1초 더 쓰더라도 제대로 분류하면 나중에 다시 찾는 시간(최저점 ⑥)이 줄어든다. 반론 ④(중복)에는 — 기존 태그를 먼저 보여 주고 새 태그는 맨 끝에 둬서, 있는 태그를 먼저 쓰게 유도한다. |
| 결론 | **수정(구현)** — ‘+ 새 태그’ · ‘+ 새 보드’ 칩 → 이름 입력 창 → 바로 선택. 화면에만 보이고 저장하지 않는다 |
| 근거(P번호·리뷰) | P03 사용자 통제 — 정해진 틀에 갇히지 않는다 · P07 유연성 — 맞는 보드가 없을 때 시트를 떠나지 않는다 · P04 일관성 — 태그와 보드를 같은 방식으로 · 최저점 ⑥ “찾고 싶은 핀이 어디 있는지 잘 모르겠어요” (2026-08-14 ★5) — 저장 시점의 분류가 다시 찾기를 돕는다 |
| 전·후 화면 | 전: 기존 보드 · 태그만 고르기 / 후: ‘+ 새 보드’ · ‘+ 새 태그’ (S-3 저장 시트 캡처, S3-4·S3-5) |

### 쟁점 7 — Pinterest에도 ‘저장한 아이디어 검색’이 있는데 스와치가 필요한가

| 칸 | 내용 |
